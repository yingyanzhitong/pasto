## 有证据的差异与修正

原 `0x100ae6428` 接收字符，扫描键码 `0..<128`；找到首个精确匹配后创建事件源和 key-down。key-down 存在时设置 Command，再创建 key-up，最后分别发送存在的事件至 tap 2。原版没有要求事件源和两个事件必须全部非空。

Pasto 原先只暴露查找 `v` 的 helper，`AppMain.waitForTarget` 用一个 guard 同时要求 source/down/up 成功；任意失败都跳过全部发送。这遗漏原来的部分创建失败分支。

本轮补入接收 `Character` 的真实 `f_100ae6428` 入口，保留首个匹配、无匹配不回退键码 9；允许 nullable source，按 down 标记 → 创建 up → 分别发送 down/up 的次序处理。`AppMain` 在原有请求代次、剪贴板变化、目标存活及前台目标检查后调用该入口。兼容的 `pasteKeyCode()` 仍返回 `v` 的投影。

本机 SDK 26.5 `CoreGraphics/CGEvent.h` 明确声明 `CGEventCreateKeyboardEvent` 的 source 为 nullable，已只读核实，没有调用编译器或事件 API。原诊断表示、raw 布局 helper 的缺失数据边界，以及完整目标激活/等待任务仍未等价闭合，函数保持 partial。

- `Pasteboard.swift`、`ClipboardPersistence.swift` 与既有对照报告的整文件摘要一致。
- 对绑定历史源码的 10 个相关方法逐方法比较，**8 个方法体完全一致**；`hidePanel` 含用户指定的焦点交接/内嵌确认清理，`waitForTarget` 含本轮 sender 修正，单独复核，不沿用其旧方法体结论。
- 复制的顺序仍为写剪贴板 → 增量事务保存 → Undo 清理 → 通知 → 反馈/收起；内容与时间分列保存，无变化不重复编码二进制内容。
- 文本/链接使用选项位 1，其他类型使用位 0；多选中存在文本/链接时进入统一聚合，是原版分支，未凭直觉改成另一种混合内容输出。
- 富文本按 flatRTFD/rtfd/rtf 优先恢复并清理表格属性；聚合保留 attributed input，换行只在结果已有文字时插入；RTF 导出使用完整 UTF-16 范围，失败回退纯文本。
- writer 保留输入项和类型顺序、空 Data、空项与空输入；统一 clear/write，随后记 changeCount，不将写入返回 Bool 改成新的原版失败门槛。
- 显式表示容器具有权威性，损坏或空容器不被显示文字/OCR 缓存替换；OCR 复制仍需显式入口和图像数据一致性检查。
