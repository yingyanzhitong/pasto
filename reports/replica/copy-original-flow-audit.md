# 复制后收起：Paste 原版实现对照

> 此报告保留切换 Core Data 前的调查快照。最新实现及验证见 [Core Data 对齐报告](copy-coredata-alignment.md)。

日期：2026-10-29。依据：已导出的 REA 6.7.0 / Ghidra 12.1.4 arm64 伪代码，以及原二进制的局部汇编、默认协议表和 Objective-C selector。它们是逆向证据，不是厂商的原始 Swift 源码。

## 结论

**上一轮“关闭面板后再保存全量 JSON”的方案，不是 Paste 原版的实现。** 它降低了 Pasto 面板等待写盘的时间，但只属于当前存储适配层的性能缓解，不能算原函数等价迁移。

原版正常复制成功路径先写剪贴板、处理 Core Data 事务，然后清理 Undo、发出恢复通知，最后显示复制反馈并退出激活状态。面板的关闭动画仍为 0.2 秒。恢复事务并不由动画完成回调触发。

## 实际调用链

| 环节 | 原版函数与证据 | 核对结果 |
| --- | --- | --- |
| 复制快捷键 | `0x100069fe0`，`decompiled/Paste/part-0035.c:3848` | 匹配物理 C 键及 Command；纯文本修饰符走同一复制入口 |
| 复制动作 | `0x100065ed8`，同文件 `:1046` | 调用恢复服务，成功后记录使用信息、排队显示 OSD，再调用 `NSApp.deactivate` |
| 恢复服务 | `0x1003b936c` → `0x10037a144` | 处理选中记录的表示格式，写剪贴板并更新防重复采集计数 |
| 历史更新事务 | `0x10037a144` → `0x1002ff310` → `0x10037b620` → `0x10037ade4` | 使用 `NSManagedObjectContext.performAndWait` 执行仓储更新 |
| 默认仓储派发 | `0x100eccad0 + 0x10` → `0x100ecca50`；方法槽 `+0x28` → `0x100364014` → `0x1003614c0` | 已重新读取 arm64 静态指针槽，历史类型分支进入 `0x100361ec0` |
| 历史时间与清理 | `0x100361ec0`、`0x100364108` | 倒序处理选中实体，逐个 `Date()` / `setTimestamp:`，再按历史策略清理；不是重新编码所有内容 |
| 保存 | `0x1003088e0` → `0x100302b78` → `0x100308968` → `0x10030844c` → `0x10035e614` | 事务回调成功且 `context.hasChanges` 时调用保存。`0x100c09980` 的 selector 槽解析为 **`save:`** |
| 恢复后的事件 | `0x10037a144` | 事务返回后清理共享 UndoManager，再发布恢复通知；随后回到复制动作 |
| 面板关闭 | `0x100019a84` | 使用 `0x3fc999999999999a`，即 0.2 秒滑出动画；完成回调负责关窗口和恢复状态 |

原版会在预览弹层等特定分支使用 0.1 秒调度，但这不是普通复制必须等待的“历史保存延时”，也不能用来解释 Pasto 大历史下约 200 毫秒的额外 JSON 编码耗时。

## 和当前 Pasto 的区别

| 项目 | Paste 原版默认本地路径 | Pasto 当前性能缓解 |
| --- | --- | --- |
| 存储模型 | Core Data 管理实体及变更 | 一个全量历史 JSON，包含内容与二进制表示 |
| 复制时修改 | 选中实体的恢复时间等属性，并按策略处理历史 | 改时间后重新编码、原子替换并同步整份 JSON |
| 保存与通知时机 | 仓储事务 → context.save（有变化时）→ Undo / 恢复通知 → OSD / 退出激活 | 剪贴板就绪 → 收起 → 全量 JSON 保存 → Undo / 恢复通知 |
| 收起动画 | 0.2 秒 | 0.2 秒 |

因此，上轮 72 MiB 合成历史下约 **426 → 203 ms** 的结果，只说明“把写盘从收起前移走”有效；没有消除全量保存，也改变了恢复通知及依赖它的声音、历史刷新等消费者的时机。

进一步对齐的重点应是**支持选中记录元数据的增量持久化，并恢复事务、通知、退出激活的原版顺序**。只缩短动画、换一个固定延时，或继续等动画后再保存，都不能替代这一步。需要同时保留现有 JSON 用户数据的兼容、多进程合并、分组身份及尚在开发中的同步逻辑。

本轮保留已经验证的性能缓解，没有在排查过程中替换数据库、修改应用代码、安装或发布应用。

## 核验范围

- 定向读取并核对 18 个成功导出的原函数；成功路径顺序与保存条件检查通过。未触碰指定跳过的失败地址。
- 默认仓储 witness 和保存 selector 已由二进制重新核实。当前安装的 Paste arm64 切片与研究切片 SHA-256 一致：`871f00354fbb1c165d858a98e6d19d6f43cb9d3f9f958b3e07c7f07eb5c19afb`。
- 原函数路径、行号、文件哈希与结论见 [JSON 证据](copy-original-flow-audit.json)。局部汇编和槽值检查保存在忽略的 `.local/copy-original-review/`。
- 本轮没有运行原版性能基准，也没有证明其所有物理磁盘刷写的完成时点、SQLite I/O 量或任意运行时 DI 替换。Core Data 保存调用已确认，不将其泛称为“后台异步保存”。
- 原版分组转入历史的实体身份、共享/清理策略和全部错误分支仍有未闭合项；本轮不增加完整函数迁移计数。
